## 2. [P0] 작품(Piece) 상세 화면 신설

### 문제

ClassicMap의 데이터 모델은 `Composer → Piece → PerformanceSector → Performance` 계층인데, **Piece에 대응하는 화면만 없습니다.** 현재 곡은 작곡가 상세의 목록 항목이거나 비교 화면의 선택 대상일 뿐, 곡 자체를 볼 수 있는 URL이 없습니다.

이 때문에:
- 곡을 공유할 수 없습니다
- 검색 결과에서 곡을 클릭했을 때 갈 곳이 없습니다 (커맨드 팔레트가 성립하지 않습니다)
- 아티스트 상세의 "이 아티스트의 연주 비교" 카드에서 작품을 눌렀을 때 갈 곳이 없습니다

### 제안

`app/piece/[id].tsx` 신설.

```
┌────────────────────────────────────────────────┐
│ 작곡가 아바타 · 작곡가명 (링크)                  │
│ 곡명 (text-display)                             │
│ Op. 18 · 1901년 작곡 · 약 35분 · 난이도 ●●●○○   │
│ [즐겨찾기] [비교하기] [Spotify] [Apple Music]   │
├────────────────────────────────────────────────┤
│ 개요                                            │
│  설명 (description)                             │
├────────────────────────────────────────────────┤
│ 비교 구간 (PerformanceSector 목록)              │
│  1악장 Moderato        연주 5개  [비교하기]     │
│  2악장 Adagio          연주 3개  [비교하기]     │
│  3악장 Allegro         연주 4개  [비교하기]     │
├────────────────────────────────────────────────┤
│ 이 곡의 연주자 (Performance credits 집계)        │
│  아바타 그리드                                   │
├────────────────────────────────────────────────┤
│ 관련 음반 / 관련 공연 (프로그램에 이 곡 포함)     │
└────────────────────────────────────────────────┘
```

- 데스크톱: 좌측 메타 패널(280) + 우측 콘텐츠 2열
- "비교하기"는 `/(tabs)/compare?composerId=&pieceId=&sectorId=`로 이동 (기존 URL 파라미터 처리 로직 재사용)

### 백엔드

- 1단계: `PieceAPI.getById` + `PerformanceSectorAPI.getByPiece` + `PerformanceAPI.getByPiece`로 **추가 없이 구현 가능**
- 2단계(선택): "이 곡을 프로그램에 포함한 공연" 조회 — `GET /pieces/{id}/concerts`. **현재 계약에 없으므로 백엔드 확정 전까지 이 섹션은 렌더하지 않습니다.**

### 주의 — **2026-09-12 갱신: 확인 완료**

채움률 확인이 끝났습니다(리디자인 보고서 1.6.4). 라흐마니노프 152곡 표본에서 `description`, `opusNumber`, `compositionYear`, `difficultyLevel`, `durationMinutes`, `spotifyUrl`, `appleMusicUrl`이 모두 채워져 있습니다. **위 화면 스케치를 그대로 구현하면 됩니다.**

추가 확정 사항:
- `difficultyLevel`은 **1~10 스케일**입니다(관측 최대 10). 별 5개가 아니라 **10단계 막대 또는 `10/10` 수치**로 표기합니다
- `youtubeMusicUrl`은 대체로 `null`이므로 버튼을 조건부 렌더합니다
- `type`이 `"album"` / `"song"`으로 옵니다. 협주곡·변주곡 같은 다악장 작품이 `"album"`입니다
- **`/composers/{id}` 상세의 `majorPieces`는 빈 배열**입니다. 작곡가의 작품 목록은 반드시 `/composers/{id}/pieces`를 씁니다

## 3. [P0] 전역 커맨드 팔레트 통합 검색

리디자인 보고서 6.3에 UI 스펙이 있습니다. 여기서는 데이터 측면만 다룹니다.

### 1단계 — 백엔드 변경 없이

기존 검색 API 3종을 병렬 호출합니다.

```
ComposerAPI.search({ q, limit: 5 })
ArtistAPI.search({ q, limit: 5 })
ConcertAPI.search({ q, limit: 5 })
```

- 300ms 디바운스, `AbortController`로 이전 요청 취소
- 곡 검색은 현재 전역 엔드포인트가 없습니다. `PieceAPI.getByComposer`만 존재합니다 → 1단계에서는 곡 그룹을 표시하지 않거나, 작곡가 검색 결과를 확장했을 때만 그 작곡가의 곡을 보여줍니다

### 2단계 — 통합 검색 엔드포인트 (백엔드 필요)

```
GET /search?q=&types=composer,piece,artist,concert,venue&limit=5
→ { composers: [...], pieces: [...], artists: [...], concerts: [...], venues: [...] }
```

요구사항:
- 곡은 `title`, `titleEn`, `opusNumber`로 검색되어야 합니다
- 국제 시드 확장을 감안해 **영문/원어 표기 모두 매칭**되어야 합니다 (예: "Rachmaninoff" / "라흐마니노프" / "Рахманинов")
- 응답에 각 항목의 라우팅 정보(type + id)와 표시용 최소 필드(이름, 썸네일, 보조 텍스트)만 포함

### 부가

- 최근 검색·최근 방문 5개를 AsyncStorage에 저장하고 빈 쿼리 시 표시
- 액션 항목(테마 전환, 화면 이동, 관리자 액션)은 클라이언트 정적 목록

## 4. [P0] 비교 A/B 동기 전환 재생

### 문제

이 앱의 유일한 차별화 기능인 "연주 비교"가, 현재는 **연주를 하나씩 따로 재생**하는 형태입니다. 가로 페이징이라 두 연주를 동시에 볼 수도 없습니다. 실제로 해석 차이를 느끼려면 **같은 지점을 번갈아 들어야** 합니다.

### 제안

비교 화면(데스크톱 그리드 / 모바일 리스트)에 **A/B 전환 컨트롤**을 추가합니다.

```
   ┌──────────────────────────────────────┐
   │  ▶  ──────●───────────────  1:24 / 4:12│   ← 공통 트랜스포트
   │  [A 조성진]  [B 임윤찬]  [C 조성진'19] │   ← 탭하면 같은 위치에서 전환
   │  ⇄ A/B 토글 (스페이스바)               │
   └──────────────────────────────────────┘
```

동작:
1. 사용자가 연주 A를 재생합니다
2. B를 누르면 **A의 현재 재생 위치 비율을 B에 매핑**해서 그 지점부터 재생합니다
3. A는 일시정지(로드 상태는 유지)
4. 키보드: `Space` = A/B 토글, `1~4` = 슬롯 직접 선택, `←→` = 5초 이동

### 위치 매핑 문제 (중요)

같은 악장이라도 연주 시간이 다릅니다(예: A는 4:12, B는 4:38). 두 가지 모드를 제공합니다.

| 모드 | 매핑 | 기본값 |
|---|---|---|
| 비율 매핑 | `t_B = t_A × (dur_B / dur_A)` | **기본** |
| 절대 매핑 | `t_B = t_A` | 옵션 |

비율 매핑은 템포 차이를 대략 흡수합니다. 정밀한 소절 단위 정렬은 별도 데이터(정렬 앵커)가 필요하므로 백로그입니다.

### 제약 준수

- 프로젝트 지침 "목록 진입 시 모든 영상을 동시에 로드하지 않습니다" → 슬롯은 기본 포스터 상태. 사용자가 A/B 모드를 **명시적으로 켤 때** 최대 2개까지만 로드합니다
- "clipStatus !== 'ready'인 영상은 재생 UI를 노출하지 않습니다" → 준비 안 된 연주는 슬롯 후보에서 제외
- 웹은 `<video>` (클립 서버), 네이티브는 YouTube IFrame — **재생 방식 자체는 변경하지 않습니다.** A/B 전환은 두 플레이어 인스턴스의 `currentTime`/`seekTo` 제어로 구현합니다
  - 웹: `videoRef.currentTime` 직접 제어 가능
  - 네이티브: `react-native-youtube-iframe`의 `seekTo` + `getCurrentTime` 사용. **네이티브에서는 A/B 전환 지연이 클 수 있으므로, 1차 릴리스는 웹 전용으로 하고 네이티브는 단순 전환(처음부터 재생)으로 폴백하는 것을 권장합니다**

### 백엔드

**추가 없음.** 클립의 실제 재생 길이는 `endTime - startTime`(초)으로 계산됩니다.

### 2026-09-12 실측 반영

- **슬롯 수는 3 또는 5**입니다. 섹터당 연주 수가 3개(12섹터) / 5개(3섹터)이고 4개는 없습니다. A/B 토글은 **최근 재생한 두 개 사이**를 오가고, `1`~`5` 숫자키로 직접 선택합니다
- 구간 길이가 연주마다 다릅니다. 라흐 3번 1악장 카덴챠 섹터 실측:
  ```
  임윤찬      670s → 771s  (101초)
  아티스트200  672s → 820s  (148초)   ← 47초 김
  아티스트201  672s → 764s  ( 92초)
  ```
  최대 1.6배 차이라 **비율 매핑이 기본값이어야 한다**는 근거가 됩니다. 절대 매핑을 쓰면 짧은 연주가 먼저 끝납니다
- `characteristic`이 `"오리지널 카덴챠"` / `"오시아 카덴챠"`처럼 **해석 차이를 직접 라벨링**하고 있습니다. A/B 토글 버튼에 이 라벨을 노출하면 (`[오리지널] ⇄ [오시아]`) 무엇을 비교 중인지 즉시 읽힙니다

## 19. [P0 · 신규 2026-09-12] "비교 가능한 것만" 필터 + 비교 카탈로그

### 문제

실측 결과 커버리지가 이렇습니다.

```
작곡가 112명 중 비교 보유 :   5명 (4.5%)
작품 11,294곡 중 비교 보유 :   8곡 (0.07%)
비교 섹터 15개 · 비교 연주 51개
8곡 전부 피아노 레퍼토리 (쇼팽 3 · 라흐마니노프 2 · 바흐 · 그리그 · 슈만)
```

그런데 비교 화면은 작곡가 112명을 전부 나열하고, 작곡가를 고르면 작품 전체(라흐마니노프 152곡, 바흐 1,695곡)를 나열합니다. **사용자가 무작위로 탐색하면 "0개의 연주 비교 가능"을 마주칠 확률이 99.9%입니다.** 제품의 핵심 기능이 사실상 숨겨져 있습니다.

이건 리디자인으로 해결되는 문제가 아니라 **탐색 경로 자체가 잘못된 문제**입니다.

### 제안

**A. 비교 화면의 기본값을 뒤집습니다**

- 작곡가 리스트 상단에 `[비교 가능한 작곡가만]` 토글. **기본 ON**
- 각 작곡가 항목에 비교 보유 곡 수 배지 (`쇼팽 ³`)
- 곡 리스트도 동일. 비교 보유 곡을 최상단에 pin + 나머지는 접어 둠
- 비교 없는 곡을 골랐을 때의 빈 상태에 **"비교 요청하기"** 버튼 (아래 C)

**B. 비교 카탈로그 화면 신설**

8곡이 전부라면 그걸 **자랑스럽게 한 화면에 다 보여주는 게** 맞습니다. 숨길 이유가 없습니다.

```
비교 카탈로그
┌────────────────────┬────────────────────┬────────────────────┐
│ 쇼팽 발라드 1번     │ 라흐 피협 3번       │ 라흐 피협 2번       │
│ 연주 15개 · 섹터 3  │ 연주 12개 · 섹터 4  │ 연주 9개 · 섹터 3   │
│ 호로비츠 루빈스타인 │ 랑랑 유자왕 임윤찬  │ 페도로바 유자왕 …   │
│ 키신 …              │                    │                    │
├────────────────────┼────────────────────┼────────────────────┤
│ 골드베르크 변주곡   │ 쇼팽 에튀드 op.25   │ 쇼팽 프렐류드 op.28 │
│ 연주 3개            │ 연주 3개            │ 연주 3개            │
│ 굴드 올라프손 레비트│ …                  │ …                  │
└────────────────────┴────────────────────┴────────────────────┘
```

- 라우트: `/(tabs)/compare`의 **곡 미선택 상태 기본 화면**으로. 지금은 "작곡가를 선택해주세요"만 뜹니다
- 정렬: 연주 수 내림차순
- 각 카드에서 섹터를 바로 고를 수 있게 (섹터 칩을 카드 안에)

**C. 비교 요청**

사용자가 원하는 곡을 남기게 해서 큐레이션 우선순위를 데이터로 받습니다.

- 비교 없는 곡의 빈 상태 + 작품 상세에 "이 곡 비교가 보고 싶어요" 버튼
- 집계는 관리자 대시보드(제안 16)에 표시
- 백엔드: `POST /pieces/{id}/comparison-requests`, `GET /admin/comparison-requests` (**B18**)

### 백엔드

A·B는 **추가 없이 구현 가능**합니다. `/composers/with-performances`(최대 8건 반환)로 비교 보유 목록을 받고, 작곡가/곡 리스트와 교차하면 됩니다. C만 신규 API가 필요합니다.

### 우선순위 근거

이 항목이 P0인 이유는, **비교 화면 리디자인(보고서 7.4)을 아무리 잘해도 볼 콘텐츠에 도달하지 못하면 의미가 없기 때문**입니다. 구현 비용도 낮습니다(기존 API 조합).
